# Panduan operasi dan verifikasi staging

Status: BELUM DISETUJUI UNTUK RILIS. Tidak ada deploy, migrasi, transaksi nyata, email nyata, atau panggilan AI berbayar selama perbaikan.

## Urutan staging

1. Cadangkan database dan Storage; siapkan pemulihan snapshot dan salinan aplikasi/rules terdahulu. Gunakan proyek staging terpisah dan data sintetis. Jangan memakai kredensial produksi untuk pengujian.
2. Verifikasi ID proyek serta database bernama default di firebase-applet-config.json, firebase.json, server dan environment MDRAWING_FIRESTORE_DATABASE_ID Functions. Default bernama default tidak sama dengan (default). REST fallback tidak menelusuri database lain.
3. Tetapkan identitas server dengan izin minimum. /api/health hanya melaporkan konfigurasi/inisialisasi; adminReady bukan uji read/write. Gunakan akun uji terkontrol untuk pembuktian operasi staging. Aplikasi memerlukan backend Express; deployment frontend statis saja tidak menyediakan command API.
4. Hentikan penulisan finance sementara dan rekonsiliasi data lama: pembayaran tanpa status, paidAmount/amountPaid, invoice tanpa termin, nominal pecahan/negatif, invoice berganda, dan relasi proyek/vendor/klien. Tidak ada konversi otomatis status kosong menjadi Confirmed. Simpan jejak keputusan rekonsiliasi. Command tidak memperbaiki saldo lama yang belum tersentuh.
5. Saat cutover, pensiunkan trigger finansial lama onClientPaymentWrite dan onVendorPaymentWrite serta listener finansial server lama. Jangan biarkan writer lama dan baru berjalan bersamaan. Ekspor Functions baru hanya syncClientProjects dan syncPublicDirectory (v2); verifikasi nama serta database pemicunya setelah deploy. Hapus/pensiunkan onClientWrite lama setelah memastikan penggantinya bekerja. Tidak ada perintah penghapusan otomatis dalam paket.
6. Deploy rules, indeks dan API sebagai satu rilis terkoordinasi. Rules melarang write finansial/quotation/proyek dari browser. Client lama akan ditolak, sehingga rilis harus mempertimbangkan cache browser dan sesi lama. Tunggu indeks siap dan periksa error query; emulator tidak membuktikan indeks produksi.
7. Storage langsung tetap deny. Firebase Storage cross-service rules hanya dapat membaca Firestore (default), sedangkan aplikasi ini memakai named database default. Pilih migrasi terkontrol atau bangun proxy server berotorisasi dan pengujian upload/read/delete; jangan sekadar mengganti isSignedIn menjadi true. Lampiran saat ini berupa URL, tidak ada pipeline upload teruji. Objek dengan download token publik lama harus ditinjau/dirotasi terpisah; rules bukan pencabut URL token yang telah dibagikan.
8. Isi dan verifikasi nama/alamat perusahaan, penandatangan, nomor pajak dan rekening penerima sebelum menerbitkan PDF. Template bawaan tidak berisi rekening dummy. Periksa PDF panjang multi-halaman, logo, alamat, pembulatan dan nominal dengan pemilik keuangan; empat uji PDF lokal tidak menggantikan pemeriksaan visual dokumen resmi.
9. Jika AI dibutuhkan, atur AI_ENABLED=true, kunci provider server, batas token/budget dan harga plafon konservatif tertinggi semua model (termasuk konversi IDR). Reservasi biaya tidak dikembalikan otomatis setelah kegagalan; sengaja konservatif. Ini plafon aplikasi berbasis konfigurasi, bukan jaminan tagihan provider. Aktifkan alert/limit akun provider secara terpisah. Model/versi dan respons tool provider nyata belum diuji.
10. Atur SMTP dengan TLS sertifikat valid. MAIL_PREVIEW hanya non-produksi. ACCEPTED_BY_SMTP berarti server SMTP menerima, bukan delivered; UNKNOWN tidak diulang otomatis. Rekonsiliasi outbox dengan log provider sebelum mengirim lagi. Batas aplikasi 100 reminder/proyek/hari; template hanya ke PIC tersimpan. Tidak ada scheduler eksternal yang dibuat.
11. Uji end-to-end sebagai OWNER, ADMIN, FINANCE, PROJECT_LEADER, TEAM, VIEWER, inactive dan akun demoted. Gunakan dua akun untuk maker/checker; periksa audit dan saldo pada retry, tab ganda, timeout dan reversal. Uji wizard resume, transmittal, impor spreadsheet rusak/besar, logout saat berpindah panel, dan pembaruan data lintas panel.
12. Jalankan beban representatif (banyak proyek/gambar, perangkat rendah, jaringan lambat). Batas API daftar 2000 proyek/penawaran dan 10000 gambar setup mengembalikan error eksplisit; belum ada paging produk penuh. Listener besar dan bundle utama sekitar 1.3MB minified masih memerlukan pengukuran staging. Notifikasi dibaca berkala dan dismiss disimpan per pengguna/per browser, belum sinkron lintas perangkat.
13. Periksa npm audit root produksi dan Functions sebelum rilis. Audit sesi ini: produksi root 0, Functions 0; lima moderate pada alat pengembangan Firebase CLI masih terbuka. Jangan deploy node_modules dev. Tidak memaksa override major OpenTelemetry karena berisiko mematahkan CLI.
14. Uji HTTPS, origin, reverse proxy, session revocation, backup/restore, pemantauan error dan rollback. Google AI Studio harus mendukung server identity/environment dan backend Express untuk pola ini. Setelah semua bukti staging dilampirkan, pemilik aplikasi/finance memberikan keputusan rilis.

## Pemulihan

Jika saldo tidak cocok, tahan konfirmasi transaksi dan rekonsiliasi audit+receipt sebelum retry. Jangan menghapus commandReceipts, financialAuditLogs atau outbox untuk memaksa ulang. SetupJobs dapat dilanjutkan dengan payload tersimpan tanpa menimpa gambar yang sudah berkembang. Batch template besar dipotong dan melaporkan jumlah berhasil, tetapi belum semua operasi template memiliki pemulihan job otomatis; periksa hasil parsial sebelum mengulang.
